- [2026-11-07] [P0] **Data surprise — Open-Meteo timezone (DST offset).** Rule: request `timezone=GMT` with `timeformat=unixtime`, pad each yearly chunk by `weather_pad_days: 1` on both sides, and convert unix seconds to New York wall-clock time in `stg_weather` with the IANA tz database (DuckDB ICU) — requesting `timezone=America/New_York` as PLAN Phase 0 task 3 literally says rejected: it attaches every DST-period reading to the wrong hour. Full record:
  - *What the API does.* For `timezone=America/New_York` the archive API applies one fixed offset, −18000 s (EST), to every date, including summer dates where the true offset is −14400 s (EDT). Its local-time labels are therefore correct in winter and wrong by one hour in DST: the value labelled `HH:00` is the reading for `HH+1:00` local time. A pipeline that joins on those labels pairs the demand of hour H with the weather of hour H+1.
  - *How it was detected.* (1) The first smoke build of `stg_weather` (October 2024 requested with `timezone=America/New_York`, unix times) started at 2024-10-01 01:00 and ended at 2024-11-01 00:00 local instead of 00:00–23:00: the API's day boundary was EST midnight, one hour after EDT midnight. (2) A direct request for 2024-07-01 reported `utc_offset_seconds: -18000` and returned its first hour at 05:00 UTC; the same request with `timezone=GMT` started at 00:00 UTC. (3) The evidence is now reproducible by code: `scripts/probe_open_meteo_offset.py` requests five days both ways and matches the local-labelled temperatures against the GMT series at shifts −2…+2 h. Result in `results/open_meteo_offset_probe.json`: the API reported the same offset (−18000 s) on all five days; on all 4 DST days probed (2024-03-11, 2024-07-01, 2024-10-01, 2024-11-02) the local labels match the GMT series exactly only at a +1 h shift (`true_hour_minus_label_hours = 1`), and on the 1 EST day probed (2024-01-15) only at 0 h.
  - *Which months are affected.* Every hour inside US daylight saving time: from the second Sunday of March 02:00 to the first Sunday of November 02:00, every year of the data (2019–2026). That is most of March, all of April–October and the first days of November; December–February are unaffected. The probe covers one EST day and four DST days in 2024 (spring, summer, autumn, last DST day); other years follow the same tz rule and are checked indirectly by the coverage test below on the full download.
  - *Tests that guard it.* (a) `tests/test_download.py::test_weather_request_uses_gmt_unixtime_and_padding` fails if the request stops asking for GMT unix seconds or drops the ±1-day pad. (b) `dbt/tests/assert_weather_covers_grid.sql` fails if any local hour of the demand grid has no weather row; it was written after the fix, but it would have failed on the unfixed October 2024 build, whose `stg_weather` began at 01:00 and so had no row for the grid hour 2024-10-01 00:00 (not re-run against the unfixed build). Limit: (b) catches a shifted *window* but not mislabelled values inside a covered window, which is why (a) guards the request itself and the probe documents the value-level shift.
  - *Consequence for the old project.* The course project used the same API with `timezone=America/New_York` and local-time strings (PLAN §2), so its weather features were most likely offset by one hour during DST. This is an inference from the API behaviour, not checked against the old code.
